# Runbooks

Пять сценариев, ради которых дежурного будят ночью. Каждый устроен одинаково:
признак, быстрая проверка, диагностика, действие, профилактика.

## Чем диагностировать

**Логи** - основной инструмент. Формат структурный (`slog`), у каждого RPC есть
`correlation_id`: он берётся из заголовка `x-correlation-id` или генерируется
сервисом и в любом случае возвращается клиенту в заголовке ответа. Если
интегратор прислал идентификатор из своего инцидента, вся история запроса
достаётся одним `grep`.

```bash
docker compose logs mediaservice | grep <correlation-id>
```

**SQL** - второй инструмент и единственный способ увидеть состояние очереди.

```bash
docker compose exec postgres psql -U media -d media
```

**Метрики** отдаются на `HTTP_ADDR` по `/metrics` в формате Prometheus:

```bash
curl -s localhost:8080/metrics | grep ^grpc_
```

Три метрики про gRPC: `grpc_requests_total` с метками `method` и `code`,
`grpc_request_duration_seconds` с меткой `method`, и `grpc_active_streams` без
меток. Первая из них - самый быстрый способ увидеть всплеск конкретного кода:

```bash
curl -s localhost:8080/metrics | grep 'code="ResourceExhausted"'
```

Счётчики остальных подсистем - `media_upload_disk_full_total`,
`media_reaper_*`, `reconciler_*` и прочие - регистрируются в том же
`prometheus.DefaultRegisterer` и попадают в ту же выдачу.

Эндпоинт аутентификации не требует, как и обе health-пробы: порт `HTTP_ADDR`
обязан жить в служебной сети.

## 1. ENOSPC: кончилось место под временные файлы

### Признак

Загрузки падают с `RESOURCE_EXHAUSTED`. В логе:

```
upload: disk full (ENOSPC)
upload: insufficient disk space: 41943040 bytes available, 104857600 required
```

### Сначала отличить от квоты и от лимита

`RESOURCE_EXHAUSTED` приходит по четырём разным поводам, и это четыре разных
инцидента. Различать по тексту ошибки:

| Текст ошибки | Что это | Кто чинит |
|---|---|---|
| `storage quota exceeded: ...` | Квота владельца | Владелец |
| `rate limit exceeded` | Лимит запросов | Вызывающий или дежурный |
| `upload: disk full (ENOSPC)` | Нет места на разделе | Дежурный |
| `upload: insufficient disk space: ...` | Резерв пробит | Дежурный |

Rate limit к диску отношения не имеет и разбирается отдельно - см. runbook 5.

Владелец чинит первый случай сам: удалить лишнее или попросить поднять квоту.

Третий случай - не отказ диска, а предохранитель `UPLOAD_RESERVE_BYTES`: места
ещё есть, но меньше резерва, и сервис отказал в загрузке заранее, чтобы не
забить раздел до нуля и не утащить за собой всё остальное. Срочность меньше,
чем у второго, но разбираться всё равно дежурному.

Третий случай - это не отказ диска, а именно тот предохранитель, ради которого
`UPLOAD_RESERVE_BYTES` существует. Сервис отказал в загрузке заранее, чтобы не
забить раздел до нуля и не утащить за собой всё остальное.

### Диагностика

```bash
docker compose exec mediaservice df -h /tmp
docker compose exec mediaservice du -sh /tmp/media-uploads /tmp/processing
docker compose exec mediaservice ls -la /tmp/media-uploads | head -30
```

Два каталога, и в дефолтной конфигурации они на одном разделе:
`UPLOAD_TEMP_DIR=/tmp/media-uploads` - приём, `PROCESSING_TEMP_DIR=/tmp/processing`
- рабочие файлы ffmpeg. Место мог съесть любой из них, лечатся они по-разному.

Дальше - определить, мусор это или живые файлы. Уборщик удаляет файлы старше
`UPLOAD_STALE_GRACE` (1 час) каждые `UPLOAD_CLEANUP_INTERVAL` (10 минут) и
пишет об этом:

```bash
docker compose logs mediaservice | grep -E \
  "removed stale temp file|failed to remove stale temp file|failed to check disk space"
```

- Строк «removed stale temp file» много, а место не освобождается - мусор
  копится быстрее, чем убирается: реальная нагрузка выше расчётной.
- Строк нет вообще, а старые файлы лежат - уборщик не работает. Смотреть,
  жив ли процесс и нет ли ошибок доступа к каталогу.
- Есть «failed to check disk space» - `statfs` не отработал. Сервис в этом
  случае загрузки не блокирует и идёт напролом до настоящего ENOSPC. Сам по
  себе симптом указывает на проблему с монтированием.

### Действие

1. **Немедленно.** Удалить временные файлы, которые заведомо не принадлежат
   активным загрузкам. Порог берём с запасом относительно `UPLOAD_STALE_GRACE`:

   ```bash
   docker compose exec mediaservice find /tmp/media-uploads -type f -mmin +120 -delete
   ```

   Файл активной загрузки удалять нельзя: стрим упадёт. Поэтому `-mmin +120`
   при часовом `UPLOAD_STALE_GRACE`, а не «всё подряд».

2. **Если место съел `/tmp/processing`.** Это следы упавших запусков ffmpeg.
   Убедиться, что воркеры сейчас не работают над этими файлами, и удалить
   старое тем же способом. Заодно проверить, не зависли ли задачи - см.
   runbook 2.

3. **Если мусора нет и всё занято живыми файлами** - раздел просто мал для
   текущей нагрузки. Временная мера: снизить `MAX_UPLOAD_BYTES`, чтобы один
   запрос занимал меньше. Настоящая - расширить том.

4. **Проверить восстановление:**

   ```bash
   curl -fsS localhost:8080/readyz
   ```

   `/readyz` про диск ничего не знает - он смотрит только на drain-флаг и ping
   БД, - поэтому при ENOSPC остаётся зелёным. Балансировщик трафик не уведёт.
   Единственная честная проверка - пробная загрузка.

### Профилактика

- Отдельный том под `UPLOAD_TEMP_DIR`, не корневой раздел контейнера.
- `UPLOAD_RESERVE_BYTES` не меньше `MAX_UPLOAD_BYTES`: иначе одна загрузка
  максимального размера пробьёт резерв целиком.
- Алерт на свободное место на разделе средствами инфраструктуры: гейджа
  свободного места сервис не отдаёт. `media_upload_disk_full_total` в
  `/metrics` годится как второй рубеж, но это запаздывающий сигнал - он растёт,
  когда загрузки уже падают.

## 2. Зависшая обработка

### Признак

`GetMedia` неделями возвращает `status: PROCESSING`. Производные не появляются,
`READY` не наступает, `error` пуст.

### Важно: не всякий «не READY» - авария

Объект, загруженный **без** `make_thumbnail` и `transcode`, остаётся в статусе
`STORED` навсегда. Задач у него нет, обрабатывать нечего, `READY` он не
достигнет никогда. Это штатное конечное состояние, а не зависание.

Зависание - это именно `PROCESSING` без движения.

### Диагностика

Состояние очереди по конкретному объекту:

```sql
SELECT id, type, status, attempts, locked_by, lease_until, run_after, last_error
FROM processing_jobs
WHERE media_id = '<media_id>';
```

Статус media пересчитывается из задач (`recalcMedia` в `internal/repo/job.go`)
по простому правилу: есть хоть одна `failed` - media `failed`; все `done` -
media `ready`; иначе - `processing`. Диагноз зависит от того, что в очереди:

**Строк нет вообще.** Задачи не создавались: обработку не просили либо запись
появилась в обход `Upload`. Media останется в `processing` навсегда, чинится
только вручную.

**`status = running`, `lease_until` в прошлом.** Воркер умер, не отпустив
аренду. Штатная ситуация, разбирается сама - см. ниже.

**`status = running`, `lease_until` в будущем и растёт.** Воркер жив и
работает. Не зависание, а долгая задача.

**`status = queued`, `run_after` в прошлом.** Задача ждёт воркера, а его нет.
Движок не работает.

**`status = queued`, `run_after` в будущем.** Задача на паузе после неудачи.
Ждать до `run_after`.

**`attempts >= JOB_MAX_ATTEMPTS`.** Попытки исчерпаны, причина в `last_error`.

Общая картина по всей очереди:

```sql
SELECT status, count(*), min(run_after), max(attempts)
FROM processing_jobs GROUP BY status;

SELECT count(*) FROM processing_jobs
WHERE status = 'running' AND lease_until < now();
```

### Механизм самовосстановления

Задачи с протухшей арендой движок возвращает в `queued` сам: на старте
(`RecoverStaleJobs`) и периодически из своей reaper-горутины. За тик берётся не
больше `JOB_REAP_BATCH_SIZE` задач. В логе это видно:

```bash
docker compose logs mediaservice | grep -E \
  "startup recovery completed|reaper: recovered expired leases|reaper: failed to recover stale jobs"
```

Значит на диагноз «running с протухшей арендой» правильная реакция в большинстве
случаев - подождать один-два `POLL_INTERVAL` и перепроверить. Если счётчик не
шевелится, движок не работает, и это уже другой инцидент.

### Действие

1. **Убедиться, что движок жив.** На старте он пишет `all components started
   successfully`. Ошибка `start processing engine` означает, что процесс вообще
   не поднялся - смотреть причину выше по логу.

2. **`queued` копится, `running` пусто.** Feeder не доливает задачи. Перезапуск
   сервиса безопасен: `queued`-задачи никуда не денутся, а `running` с протухшей
   арендой подберёт startup recovery.

3. **Задача исчерпала попытки.** Читать `last_error`. Типичные причины: файл
   не разбирается ffmpeg, кончилось место под `PROCESSING_TEMP_DIR`, недоступно
   хранилище. Починив причину, задачу можно вернуть в очередь вручную:

   ```sql
   UPDATE processing_jobs
   SET status = 'queued', attempts = 0, run_after = now(),
       locked_by = NULL, lease_until = NULL, last_error = NULL
   WHERE id = '<job_id>';
   ```

   Media при этом останется `failed` до следующего пересчёта - он произойдёт,
   когда задача завершится.

4. **Задач нет, а media в `processing`.** Автоматики на этот случай нет.
   Перевести объект в конечное состояние вручную, предварительно убедившись,
   что оригинал в хранилище на месте:

   ```sql
   UPDATE media SET status = 'stored' WHERE id = '<media_id>' AND status = 'processing';
   ```

   `stored`, а не `ready`: производных нет, и обещать их клиенту нельзя.

5. **Массовое зависание после аварийной остановки.** Нормальный ход - все
   `running` с протухшими арендами вернутся в `queued` пачками по
   `JOB_REAP_BATCH_SIZE`. Если задач тысячи, а батч сто, разбор займёт время;
   на период разбора батч можно поднять.

### Профилактика

- `JOB_LEASE` заметно больше типичного времени обработки, иначе живую задачу
  подберёт второй воркер и один файл обработается дважды.
- `JOB_TIMEOUT` покрывает самый долгий ожидаемый транскод задачи целиком.
  Отдельный потолок на один запуск ffmpeg задаётся `FFMPEG_TIMEOUT`.
- Помнить про `uq_processing_jobs_media_id_type`: на пару (media, тип) задача
  ровно одна, повторная постановка идемпотентна.

## 3. Сверка удалений

### Признак

Один из двух перекосов между БД и хранилищем:

- записи висят в статусе `deleting` и не исчезают;
- в MinIO лежат объекты, которым не соответствует ни одна строка в `media`
  (сироты), и место расходуется впустую.

### Кто этим занимается

Reconciler, горутина внутри процесса, тик раз в `RECONCILER_INTERVAL` (5 минут).
Делает две вещи подряд:

1. **Дочищает `deleting`.** Берёт записи старше `RECONCILER_GRACE_PERIOD`,
   удаляет объекты по префиксу `{owner_id}/{media_id}/`, затем удаляет строку.
2. **Ищет сирот.** Обходит хранилище, для каждого объекта проверяет наличие
   записи и удаляет то, чему записи нет.

Тики не наслаиваются: если предыдущий ещё идёт, следующий пропускается с
`reconciler tick skipped: previous tick still running` в логе. Регулярное
появление этой строки само по себе диагноз - тик не укладывается в интервал.

Паника внутри тика гасится `recover()` и роняет только сам тик: в логе
появляется `panic in reconciler tick` со стеком, процесс продолжает работать.

### Диагностика

```sql
SELECT id, owner_id, status, updated_at, now() - updated_at AS age
FROM media WHERE status = 'deleting' ORDER BY updated_at LIMIT 50;
```

```bash
docker compose logs mediaservice | grep -E \
  "reconciler tick (started|finished|skipped)|panic in reconciler tick" -e \
  "deleted media and objects|deleted orphan object|ownership guard" -e \
  "orphan scan failed|process deleting media failed"
```

Возраст записи важнее самого факта. Запись в `deleting` моложе
`RECONCILER_GRACE_PERIOD` - это норма: удаление идёт, до неё просто ещё не
дошли руки. Старше - разбираться.

### Действие

1. **Reconciler вообще не тикает.** Строк `reconciler tick started` в логе нет.
   Горутина стартует в `main.go` безусловно, поэтому её отсутствие означает, что
   не поднялся весь процесс.

2. **`RECONCILER_DRY_RUN=true`.** Тогда в логе будут `dry-run: would delete
   media` и `dry-run: would delete orphan`, а удалений - ни одного. Ровно то
   поведение, ради которого флаг и есть. Посмотреть на объём в логах и снять
   флаг, когда цифры не пугают.

3. **`ownership guard` в логе.** Запись не обрабатывается, потому что её
   `storage_key` не начинается с `{owner_id}/{media_id}/` либо ключ вне
   служебного префикса. Это предохранитель против удаления чужого: reconciler
   отказывается трогать то, чья принадлежность не доказана. Разбирать руками, не
   ослабляя проверку - она стоит между багом в ключе и потерей чужих данных.

4. **`orphan check: UploadStartedAt is zero, skipping`.** У объекта в хранилище
   нет метки старта загрузки, и вычислить grace невозможно. Reconciler
   пропускает его, чтобы не удалить файл активной загрузки. Такие объекты
   накапливаются и не убираются никогда - разбирать отдельно, вручную.

5. **Ручное добивание конкретной записи** после того, как стало понятно, что
   объектов в хранилище уже нет:

   ```sql
   DELETE FROM media WHERE id = '<media_id>' AND status = 'deleting';
   ```

   `media_derivative`, `processing_jobs` и `media_attachments` уйдут каскадом по
   внешним ключам. Учёт занятого места поправит триггер `trg_media_storage_quota`.

### Отдельно: «удалил, а объект на месте»

Если `DeleteMedia` вернул `OK`, а файл в хранилище остался, - это не сбой.
Метод снимает привязку конкретного владельца, а физическое удаление наступает,
только когда снята последняя. Проверять надо счётчик:

```sql
SELECT m.id, m.status, m.usages_count,
       (SELECT count(*) FROM media_attachments a WHERE a.media_id = m.id) AS attachments
FROM media m WHERE m.id = '<media_id>';
```

`usages_count > 0` - объект жив законно, к нему привязан кто-то ещё.
`usages_count = 0` при статусе `deleting` - удаление начато и его дочистит
reconciler, см. выше.

Если же `DeleteMedia` вернул `NOT_FOUND`, значит запись существует, но
вызывающий к ней не привязан: обычно это попытка удалить чужое, реже -
неверный `x-owner-id` у посредника.

### Профилактика

- `RECONCILER_GRACE_PERIOD` не снижать: он защищает объекты незавершённых
  загрузок. Grace меньше времени долгой загрузки означает удаление файла у
  живого клиента.
- Первый выкат - с `RECONCILER_DRY_RUN=true`.
- Следить за `reconciler tick skipped`: обход всего хранилища дорожает вместе
  с его ростом.

## 4. Клиент упирается в лимит

### Признак

Вызывающий жалуется на `RESOURCE_EXHAUSTED` там, где раньше всё работало, при
том что места на дисках достаточно и квота не выбрана.

### Сначала отличить от квоты и диска

`RESOURCE_EXHAUSTED` приходит по четырём разным поводам. Различать по тексту:

| Текст ошибки | Что это |
|---|---|
| `rate limit exceeded` | Лимит запросов в секунду |
| `too many active streams` | Лимит одновременных стримов |
| `storage quota exceeded: ...` | Квота владельца |
| `upload: disk full (ENOSPC)` | Runbook 1 |

### Диагностика

```bash
curl -fsS localhost:8080/metrics \
  | grep 'grpc_requests_total.*code="ResourceExhausted"'
curl -fsS localhost:8080/metrics | grep '^grpc_active_streams'
```

Дальше главный вопрос: **попал ли вызывающий в общее ведро.** Лимиты ключуются
по `x-caller-id`, но значение, которого нет в `CALLER_ID_ALLOWLIST`,
схлопывается в общий ключ `authenticated` вместе со всеми остальными. У
`CALLER_ID_ALLOWLIST` дефолта нет, поэтому в свежей установке это происходит со
всеми сразу.

Проверить, что в конфиге:

```bash
docker compose exec mediaservice env \
  | grep -E 'CALLER_ID_ALLOWLIST|RATE_LIMIT_BURST'
```

Пустой вывод означает, что переменные не заданы. В дампе конфига из логов их
не видно: `Config.String()` печатает `RateLimitRPS` и `MaxConcurrentStreams`,
но `CallerIDAllowlist` и `RateLimitBurst` пропускает.

### Действие

1. **Список пуст или в нём нет этого клиента.** Самый частый случай: лимит
   выглядит как персональный, а работает как общий. Добавить caller ID в
   `CALLER_ID_ALLOWLIST` и перезапустить - у клиента появится своё ведро.
2. **Клиент не шлёт `x-caller-id`.** Тот же эффект. Чинится на стороне клиента.
3. **Ведро своё, но лимита не хватает.** Поднять `RATE_LIMIT_RPS`. Если жалоба
   на всплески, а не на среднюю нагрузку, поднимать `RATE_LIMIT_BURST`: он
   определяет, сколько запросов можно сделать залпом после простоя.
4. **`too many active streams`.** Клиент держит больше
   `MAX_CONCURRENT_STREAMS` одновременных `Upload` или `DownloadStream`.
   Проверить, закрывает ли он потоки: незакрытый стрим держит слот до разрыва
   соединения.

### Профилактика

- Перечислять в `CALLER_ID_ALLOWLIST` все системы поимённо. Иначе лимит на
  вызывающего превращается в лимит на сервис.
- Помнить, что `x-caller-id` не верифицируется: знающий чужой ID займёт чужое
  ведро. Заголовок должен проставлять доверенный посредник.

## 5. Kafka DLQ

### Признак

В топике `KAFKA_DLQ_TOPIC` (по умолчанию `media.events.dlq`) копятся сообщения.
Прикладной эффект - привязки и открепления, которые ожидались, не произошли.

### Что туда попадает

Основной поток при этом **не встаёт**: offset коммитится, обработка идёт
дальше. Это сознательный выбор - одно неисправимое событие не должно
останавливать очередь.

| Причина | `dlq_reason` |
|---|---|
| Конверт не разобран | `invalid envelope: ...` |
| Конфликт отпечатка | `fingerprint conflict` |
| Исчерпаны попытки | `max attempts (3) exceeded: ...` |
| Неисправимая ошибка | текст ошибки |

**Конверт не разобран** - невалидный JSON либо не прошёл `Validate()`.
Идентификатор для DLQ вычисляется детерминированно из тела, потому что своего
`event_id` у такого сообщения нет.

**Конфликт отпечатка** - тот же `event_id` пришёл с другим телом, то есть
отправитель переиспользовал идентификатор.

**Исчерпаны попытки** - ошибка классифицирована как временная, но повторы не
помогли.

**Неисправимая ошибка** - `PermanentError`, например неизвестный `event_type`.

У каждого сообщения в DLQ есть заголовки `dlq_reason` и `dlq_timestamp`, ключ -
`event_id`, тело - исходное сообщение байт в байт.

### Диагностика

Причины видны и из Postgres, без чтения топика:

```sql
SELECT event_id, status, retry_count, result->>'reason' AS reason, updated_at
FROM processed_events
WHERE status = 'dlq'
ORDER BY updated_at DESC LIMIT 50;

SELECT result->>'reason' AS reason, count(*)
FROM processed_events WHERE status = 'dlq' GROUP BY 1 ORDER BY 2 DESC;
```

Зависшие в обработке события - отдельный симптом:

```sql
SELECT event_id, owner, retry_count, lease_expires_at
FROM processed_events
WHERE status = 'processing' AND lease_expires_at < now();
```

Само содержимое DLQ:

```bash
docker compose exec kafka rpk topic consume media.events.dlq \
  -X brokers=localhost:9092 --num 20 --format '%v %h\n'
```

Логи:

```bash
docker compose logs mediaservice | grep -E \
  "dlq publish failed|mark dlq|claim failed|event already processed"
```

### Действие

Разбор зависит от причины и в трёх случаях из четырёх сводится к разговору с
отправителем, а не к правке у себя.

1. **`invalid envelope` или `fingerprint conflict`.** Виноват отправитель:
   ломаный формат либо переиспользованный `event_id`. Повторять бесполезно,
   пока он не исправится.

2. **`unknown event type`.** Поддерживаются ровно `media.attach` и
   `media.detach`. Всё остальное - неисправимо по определению.

3. **`max attempts exceeded`.** Единственная причина, где виновата наша
   сторона. Смотреть исходную ошибку в `dlq_reason`: недоступна БД, недоступно
   хранилище, media ещё не существует. После починки событие имеет смысл
   переиграть.

4. **`dlq publish failed` в логе.** Худший случай: событие не обработалось и в
   DLQ не уехало. Offset **не** коммитится, поток встаёт на этом сообщении и
   будет его перечитывать. Чинить доступность DLQ-топика немедленно - иначе
   consumer не двинется.

### Переигрывание события

Порядок обязателен и именно такой:

```sql
-- 1. Убедиться, что запись действительно в dlq и причина понятна
SELECT event_id, result->>'reason' FROM processed_events WHERE event_id = '<event_id>';

-- 2. Снять признак обработанности
DELETE FROM processed_events WHERE event_id = '<event_id>' AND status = 'dlq';
```

```bash
# 3. Переопубликовать исходное тело в основной топик
docker compose exec kafka rpk topic produce media.events -X brokers=localhost:9092
```

Без шага 2 ничего не произойдёт: `Claim` увидит терминальный статус, вернёт
«уже обработано», и событие будет тихо пропущено с `event already processed,
skipping` в логе. Шаг 2 без шага 1 - удаление истории инцидента, после которого
причина уже не восстановится.

### Профилактика

- `RETENTION_OLDER_THAN` (30 суток) обязан с запасом превышать retention
  топика. Если запись об обработанном событии удалена раньше, чем Kafka
  перестанет его передоставлять, побочный эффект выполнится второй раз.
  Валидатор требует минимум 24 часа именно поэтому.
- Топики создавать явно, а не автосозданием на первом `produce`: авто-топик
  получает дефолтные partitions и retention кластера, и конфигурация окружения
  перестаёт быть воспроизводимой. В compose это делает шаг `createkafkatopics`.
- Разные установки сервиса - разные `KAFKA_GROUP`. Одинаковая группа означает,
  что они поделят партиции и каждая увидит лишь часть событий.
