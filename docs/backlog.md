# Бэклог: 20 задач

Основание: [ТЗ](TZ.md), [SPEC](SPEC.md).

## Как устроен бэклог

Задачи нарезаны **вертикальными слайсами**: одна задача — это фича целиком,
от gRPC-хендлера через доменную логику до репозитория и хранилища, вместе с
тестами. Разработчик делает фичу end-to-end и не ждёт, пока кто-то другой
допишет «свой слой».

Волны:
1. **infra** (1–3) и **core** (4–8) — общий фундамент. Берём первыми, это те
   задачи, от которых остальные действительно зависят. Делаются быстро и
   небольшим числом людей.
2. **feature** (9–18) — вертикальные слайсы. После фундамента берутся
   параллельно и почти не пересекаются между собой.
3. **qa** (19–20) — приёмка и документация.

У каждой задачи указано, что она трогает и от чего зависит. Если в задаче
написано «зависимостей нет» — её можно брать сразу после фундамента, не
согласовываясь с соседями.

Общее для всех задач с кодом:
- `make build`, `make lint`, `make test` зелёные.
- Тесты на новую логику: unit на домен, интеграционные (testcontainers) там,
  где есть Postgres или MinIO.
- Секреты только из env, в логи не попадают.
- Внешний контракт меняется только через `proto/media/v1` и по согласованию.

## INFRA

### 1. Каркас Go-модуля, линтер и CI
`infra` `size:M`

**Что делать.** Инициализировать `go.mod` (`module mediaservice`, Go 1.22+),
завести минимальный `cmd/mediaservice/main.go`, который просто стартует и
корректно завершается. Настроить `golangci-lint` конфигом в репозитории.
Поднять CI на GitHub Actions: сборка, `go vet`, линтер, тесты на каждый PR.

**Трогает.** `go.mod`, `cmd/mediaservice`, `.golangci.yml`, `.github/workflows`.

**Зависимости.** Нет. Блокирует всё остальное, поэтому берётся первой.

**Критерии приёмки.**
- `make build`, `make lint`, `make test` отрабатывают на чистом клоне.
- CI запускается на PR, падает при ошибке сборки, линтера или теста (проверено намеренно сломанным PR).
- Версия Go зафиксирована в `go.mod` и в CI одинаково.

### 2. Инфраструктура в docker compose
`infra` `size:M`

**Что делать.** Написать `docker-compose.yml` с Postgres, MinIO и самим
сервисом. В образе сервиса должен быть ffmpeg. Автосоздание bucket в MinIO при
старте. Подготовить `.env.example`, работающий как есть.

**Трогает.** `docker-compose.yml`, `Dockerfile`, `.env.example`.

**Зависимости.** Нужен каркас (задача 1) — только чтобы было что собирать.

**Критерии приёмки.**
- `cp .env.example .env && make up` поднимает все сервисы на чистой машине.
- В контейнере сервиса доступны `ffmpeg` и `ffprobe` (проверено `docker compose exec`).
- Bucket в MinIO создаётся автоматически, вручную ничего настраивать не нужно.
- Postgres и MinIO имеют healthcheck, сервис стартует после их готовности.
- Порты Postgres и MinIO наружу не публикуются в проде-профиле.

### 3. Конфиг, логирование, graceful shutdown
`infra` `size:M`

**Что делать.** Загрузка конфигурации из env с безопасными дефолтами и
валидацией на старте (нет обязательной переменной — внятная ошибка, а не
падение позже). Структурные логи на `log/slog` с correlation-id. Общий
механизм graceful shutdown: контекст отмены, ожидание завершения в пределах
таймаута.

**Трогает.** `internal/config`, `cmd/mediaservice`.

**Зависимости.** Задача 1.

**Критерии приёмки.**
- Все параметры из SPEC §7 читаются из env, значения по умолчанию безопасные.
- Тест: отсутствие обязательной переменной даёт понятную ошибку старта с именем переменной.
- Тест: секреты (ключи MinIO, пароль БД) не попадают в вывод логов при старте.
- По сигналу завершения процесс отдаёт управление в пределах таймаута и не оставляет висящих горутин (проверено тестом с `goleak` или аналогом).

## CORE

### 4. gRPC-контракт и кодогенерация
`core` `size:M`

**Что делать.** Описать `proto/media/v1/media.proto` по SPEC §3: сервис
`MediaService` со всеми методами, сообщения, валидация полей. Настроить
генерацию через `make proto`, сгенерированный код коммитится в репозиторий.

**Трогает.** `proto/media/v1`, `Makefile`.

**Зависимости.** Задача 1. **Это общий контракт — делается рано и один раз.**
Дальнейшие изменения контракта только по согласованию команды.

**Критерии приёмки.**
- `make proto` генерирует код воспроизводимо, повторный запуск не даёт диффа.
- В контракте присутствуют все методы из ТЗ §3, включая клиентский и серверный стримы.
- Обязательные поля описаны правилами валидации, невалидный запрос отклоняется до бизнес-логики.
- Инструкция по установке `protoc` и плагинов есть в README.

### 5. gRPC-сервер: запуск, health, перехватчики, метрики
`core` `size:L`

**Что делать.** Поднять gRPC-сервер: регистрация сервиса, стандартный
health-check, graceful stop. Цепочка перехватчиков: correlation-id, восстановление
после паники, чтение API-токена из metadata (без валидации, см. ТЗ §5),
логирование запросов, метрики Prometheus, ограничение частоты и числа
одновременных стримов на вызывающего (ТЗ §5, лимиты из конфига). Отдельный
HTTP-порт для `/metrics` и проб.

**Трогает.** `internal/api` (инфраструктурная часть), `cmd/mediaservice`.

**Зависимости.** Задачи 1, 3, 4. **Владеет цепочкой перехватчиков целиком** —
чтобы фичи потом не правили один и тот же файл.

**Критерии приёмки.**
- Сервер стартует, health-check отвечает, `/metrics` отдаёт метрики.
- Тест: паника в хендлере не роняет процесс, клиент получает internal-ошибку.
- Тест: correlation-id из metadata попадает в логи; при отсутствии — генерируется.
- Тест: превышение лимита запросов на вызывающего даёт `RESOURCE_EXHAUSTED`, другой вызывающий не затронут.
- Тест: превышение числа одновременных стримов на вызывающего отклоняется.
- Метрики покрывают количество и длительность вызовов, число ошибок по кодам.

### 6. Схема БД, миграции и пул подключений
`core` `size:M`

**Что делать.** Миграции по SPEC §6: таблицы `media`, `media_derivative`,
`processing_jobs` со всеми индексами и ограничениями. Пул `pgxpool` с настройками
из конфига, применение миграций при старте либо отдельной командой.

**Трогает.** `migrations`, `internal/repo` (подключение и общие хелперы).

**Зависимости.** Задачи 1, 3. **Владеет схемой** — фичи дальше добавляют свои
запросы, но не переписывают чужие таблицы.

**Критерии приёмки.**
- Миграции применяются на чистой базе и создают все таблицы и индексы из SPEC §6.
- Тест на testcontainers: миграции проходят, повторный запуск идемпотентен.
- Уникальный индекс `(owner_id, idempotency_key)` действительно запрещает дубль (тест на нарушение).
- Пул настраивается из env, есть таймауты подключения и запроса.
- Правило записано в README: схему меняем только новой миграцией, старые не редактируем.

### 7. Адаптер объектного хранилища (MinIO)
`core` `size:M`

**Что делать.** Обёртка над MinIO: положить объект потоком, отдать объект
потоком, presigned URL на скачивание, удалить объект, удалить префикс. Ключи
строятся по layout из ТЗ §6 от `media_id`, пользовательское имя файла в ключ
не попадает.

**Трогает.** `internal/storage`.

**Зависимости.** Задачи 1, 3.

**Критерии приёмки.**
- Интеграционные тесты на testcontainers: запись, чтение, presign, удаление.
- Тест: файл записывается и читается потоком, целиком в память не поднимается.
- Тест: presigned URL работает и протухает по истечении TTL.
- Тест: удаление несуществующего объекта не считается ошибкой.
- Тест: имя файла с путями и спецсимволами не влияет на ключ объекта.

### 8. Обёртка ffprobe и ffmpeg
`core` `size:L`

**Что делать.** Пакет для запуска `ffprobe` (определение реального типа,
кодека, длительности, разрешения, битрейта) и `ffmpeg` (генерация превью,
транскодинг, нормализация). Запуск через `exec` с аргументами массивом, без
shell. Контекст с таймаутом, корректное убийство процесса по отмене. Небольшие
фикстуры для тестов.

**Трогает.** `internal/processing` (только обёртка, без движка очереди).

**Зависимости.** Задача 1. Не зависит от БД и gRPC — можно делать параллельно
с любой другой задачей фундамента.

**Критерии приёмки.**
- Тест на фикстурах: ffprobe корректно определяет тип и метаданные для картинки, видео и аудио.
- Тест: файл с подделанным расширением определяется по реальному содержимому.
- Тест: битый файл даёт понятную ошибку, процесс не зависает.
- Тест: отмена контекста убивает дочерний процесс, зомби не остаются.
- Аргументы команд не собираются конкатенацией пользовательских строк (проверяется ревью и тестом с именем-инъекцией).

## FEATURE

### 9. Загрузка медиа (client-streaming) end-to-end
`feature` `size:L`

**Что делать.** Полный слайс загрузки по ТЗ §3.1: хендлер приёма стрима,
валидация первого сообщения, запись потока во временное хранилище, определение
реального типа через ffprobe, отклонение подделанного mime, заливка оригинала в
MinIO, запись метаданных в Postgres, идемпотентность по
`(owner_id, idempotency_key)`, постановка задачи обработки при запросе.

**Трогает.** `internal/api` (метод Upload), `internal/media`, `internal/repo`
(запросы к `media`), использует `internal/storage` и `internal/processing`.

**Зависимости.** Фундамент (4, 5, 6, 7, 8). Между фичами — нет.

**Критерии приёмки.**
- Интеграционный тест: загрузка картинки, видео и аудио создаёт объект в MinIO и запись в Postgres со статусом `stored`.
- Тест: файл больше лимита из конфига отклоняется, частично записанные данные подчищаются.
- Тест: png с телом исполняемого файла отклоняется.
- Тест: невалидный `owner_id` отклоняется до записи куда-либо.
- Тест: повтор с тем же `idempotency_key` возвращает существующий `media_id` и не создаёт дубль.
- Тест: загрузка файла заметного размера не приводит к росту потребления памяти пропорционально размеру.

### 10. Чтение метаданных и список по владельцу
`feature` `size:M`

**Что делать.** Слайс чтения по ТЗ §3.3: `GetMedia` отдаёт метаданные, статус
и список производных; `ListMediaByOwner` отдаёт страницу медиа владельца с
пагинацией и стабильным порядком.

**Трогает.** `internal/api` (методы Get/List), `internal/media`, `internal/repo`
(запросы чтения).

**Зависимости.** Фундамент. Между фичами — нет.

**Критерии приёмки.**
- Интеграционный тест: `GetMedia` возвращает метаданные и производные, для отсутствующего id — `NOT_FOUND`.
- Тест: `ListMediaByOwner` пагинирует, страницы не пересекаются и не теряют записи при вставке новых.
- Тест: чужой `owner_id` не видит записи другого владельца.
- Тест: порядок выдачи стабилен между запросами.

### 11. Ссылка на скачивание (presigned URL)
`feature` `size:M`

**Что делать.** Слайс по ТЗ §3.3: `GetDownloadURL` для вариантов `original`,
`thumbnail`, `r_720` — поиск нужного объекта, выдача presigned URL с TTL из
конфига.

**Трогает.** `internal/api` (метод GetDownloadURL), `internal/media`,
`internal/repo` (чтение производных), `internal/storage` (presign).

**Зависимости.** Фундамент. Между фичами — нет.

**Критерии приёмки.**
- Интеграционный тест: по выданному URL скачивается корректный файл.
- Тест: URL перестаёт работать по истечении TTL.
- Тест: запрос несуществующего варианта даёт `NOT_FOUND`, а не пустую ссылку.
- Тест: медиа в статусе `processing` не отдаёт ссылку на ещё не готовую производную.

### 12. Отдача файла потоком (server-streaming)
`feature` `size:M`

**Что делать.** Слайс по ТЗ §3.3: `DownloadStream` отдаёт байты чанками через
сам сервис, без прямого доступа клиента к хранилищу. Размер чанка из конфига,
корректное завершение при отмене клиентом.

**Трогает.** `internal/api` (метод DownloadStream), `internal/media`,
`internal/storage` (чтение потоком).

**Зависимости.** Фундамент. Между фичами — нет.

**Критерии приёмки.**
- Интеграционный тест: скачанный через стрим файл побайтно совпадает с загруженным.
- Тест: отмена клиентом посреди стрима освобождает ресурсы, горутины не текут.
- Тест: файл не читается в память целиком.
- Тест: запрос отсутствующего медиа даёт `NOT_FOUND` до начала стрима.

### 13. Удаление медиа и удаление по владельцу
`feature` `size:M`

**Что делать.** Слайс по ТЗ §3.5: жёсткое удаление медиа — пометка `deleting`,
очистка оригинала и всех производных в MinIO, затем удаление записей.
`DeleteByOwner` — каскадно по владельцу. Идемпотентность повторного удаления.
Фоновая уборка зависших в `deleting`.

**Трогает.** `internal/api` (методы Delete), `internal/media`, `internal/repo`,
`internal/storage`.

**Зависимости.** Фундамент. Между фичами — нет.

**Критерии приёмки.**
- Интеграционный тест: после удаления нет ни записей в БД, ни объектов в MinIO.
- Тест: повторное удаление того же медиа возвращает успех.
- Тест: сбой при очистке хранилища оставляет запись в `deleting`, и фоновая уборка доводит удаление до конца.
- Тест: `DeleteByOwner` удаляет всё медиа владельца и не трогает чужое.

### 14. Движок асинхронной обработки на горутинах
`feature` `size:L`

**Что делать.** Движок по ТЗ §3.6: буферизованный канал задач, пул воркеров с
ограничением из конфига, фидер задач из `processing_jobs` с забором через
`FOR UPDATE SKIP LOCKED`, восстановление зависших `running` при старте, ретраи
с backoff, graceful drain при остановке, метрики глубины очереди и числа
задач в работе. Движок принимает обработчики задач по типу — конкретные типы
добавляются отдельными задачами.

**Трогает.** `internal/processing` (движок), `internal/repo` (запросы к
`processing_jobs`).

**Зависимости.** Фундамент. **Задачи 15 и 16 пишут обработчики против
интерфейса движка** — чтобы не ждать друг друга, интерфейс обработчика
фиксируется в этой задаче в первую очередь и не меняется.

**Критерии приёмки.**
- Тест: одновременно выполняется не больше `WORKER_CONCURRENCY` задач.
- Тест: задачи, оставшиеся в `running` после аварийного завершения, возвращаются в `queued` при старте.
- Тест: неудачная задача повторяется с backoff, после исчерпания попыток переходит в `failed` с причиной.
- Тест: graceful shutdown доводит текущие задачи до конца либо возвращает их в очередь, горутины не текут.
- Тест: переполнение канала не теряет задачи — они остаются в БД и подхватываются позже.
- Метрики глубины очереди и числа задач в работе отдаются в Prometheus.

### 15. Генерация превью
`feature` `size:M`

**Что делать.** Обработчик задачи по ТЗ §3.2: для видео — кадр на N-й секунде
в jpg, для аудио — waveform png, для картинки — уменьшенный thumbnail.
Результат кладётся в MinIO и регистрируется как производная запись.

**Трогает.** `internal/processing` (обработчик типа задачи), `internal/repo`
(`media_derivative`), `internal/storage`.

**Зависимости.** Интерфейс обработчика из задачи 14 и обёртка ffmpeg из
задачи 8. С задачей 16 не пересекается — разные типы задач.

**Критерии приёмки.**
- Интеграционный тест на фикстурах: для видео, аудио и картинки создаётся превью нужного формата.
- Тест: производная регистрируется в `media_derivative` со ссылкой на родителя и корректным ключом в MinIO.
- Тест: битый исходник переводит задачу в `failed` с причиной, сервис продолжает работать.
- Параметры (секунда кадра, размер миниатюры) берутся из конфига.

### 16. Транскодинг и нормализация
`feature` `size:L`

**Что делать.** Обработчик задачи по ТЗ §3.2: видео — нормализованный mp4
(h264 + aac) в рендиции 720p, аудио — нормализация в mp3/aac, картинка —
resize к целевым размерам. Результат в MinIO плюс запись производной. Статус
медиа доходит до `ready`.

**Трогает.** `internal/processing` (обработчик типа задачи), `internal/repo`,
`internal/storage`.

**Зависимости.** Интерфейс обработчика из задачи 14 и обёртка ffmpeg из
задачи 8. С задачей 15 не пересекается.

**Критерии приёмки.**
- Интеграционный тест: видео транскодируется в 720p mp4, результат читается ffprobe и имеет ожидаемые кодеки.
- Тест: аудио нормализуется, картинка ресайзится к заданным размерам.
- Тест: после успешной обработки статус медиа становится `ready`.
- Тест: падение ffmpeg переводит медиа в `failed` с причиной, процесс жив.
- Тест: задача уважает таймаут из конфига и отменяется по graceful shutdown.

### 17. Время жизни медиа и фоновая уборка
`feature` `size:M`

**Что делать.** Слайс по ТЗ §3.4: приём необязательного `ttl` при загрузке,
хранение `expires_at`, фоновый reaper, который удаляет истёкшее медиа вместе с
производными той же логикой, что и обычное удаление. Без `ttl` медиа хранится
вечно.

**Трогает.** `internal/media` (reaper), `internal/repo` (выборка по
`expires_at`), переиспользует удаление из задачи 13.

**Зависимости.** Фундамент. Логику удаления берёт из задачи 13 — если та ещё
