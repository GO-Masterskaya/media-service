# gRPC API

Контракт: `proto/media/v1/media.proto`, gRPC-сервис `media.v1.MediaService`.
Другого внешнего интерфейса нет: HTTP-порт отдаёт health-пробы и `/metrics`.

Этот документ описывает поведение реализации, а не намерение. Где реализация
расходится с `docs/SPEC.md`, права реализация - расхождения помечены.

## Подготовка инструмента

Сервер **не регистрирует gRPC reflection**, поэтому `grpcurl` не может узнать
схему у самого сервиса. Схему нужно принести с собой. Контракт импортирует
`buf/validate/validate.proto`, которого в репозитории нет - он приезжает из
Buf Schema Registry, - поэтому передать `grpcurl` один файл `media.proto` тоже
не выйдет: импорт не разрешится.

Рабочий способ - собрать дескриптор через `buf` и дальше работать с ним:

```bash
buf build -o media.protoset.binpb
```

`buf` подтягивает зависимость по `buf.lock` (первый запуск - с сетью, дальше
из кеша) и складывает полный набор дескрипторов в один файл. Он wire-совместим
с `FileDescriptorSet`, и `grpcurl` принимает его как `-protoset`.

Дальше во всех примерах:

```bash
GRPCURL="grpcurl -protoset media.protoset.binpb -plaintext"
TOKEN=change-me
OWNER=$(uuidgen)
```

Тем, кто пишет на Go, проще взять сгенерированные stubs из `proto/media/v1`
(пакет `mediav1`) - см. `docs/INTEGRATION.md`.

## Заголовки

| Заголовок | Обязателен |
|---|---|
| `authorization` | Да, если `GRPC_AUTH_ENABLED=true` |
| `x-owner-id` | Да, если `STRICT_OWNER_CHECK=true` (дефолт) |
| `x-caller-id` | Нет, но см. ниже |
| `x-correlation-id` | Нет |
| `x-caller-id` | Нет, но см. ниже |

**`authorization`** - статический токен. Принимается как `Bearer <token>` и
как голый `<token>`. Health-методы проверку минуют.

**`x-owner-id`** - UUID вызывающего. Проставляет доверенный посредник; сервис
его не верифицирует.

**`x-caller-id`** - идентификатор вызывающей системы, по которому ключуются
лимиты. Формально необязателен, но без него вызов попадает в общее ведро - см.
«Лимиты» ниже. Не путать с `x-owner-id`: первый про то, какая система зовёт,
второй про то, чьи это медиа.

**`x-correlation-id`** - идентификатор для сквозной трассировки. Если не
прислан, сервис генерирует свой и в любом случае возвращает значение в
заголовке ответа.

**`x-caller-id`** - ключ, по которому считаются лимиты. Не то же самое, что
`x-owner-id`: владелец - это чьи файлы, вызывающий - это кто стучится. Без
этого заголовка запрос не отклоняется, но попадает в общее ведро лимитов
вместе со всеми остальными, см. раздел «Лимиты».

Про `x-owner-id` есть отдельная тонкость, которая ломает интуицию:
**`DeleteMedia` требует непустой `x-owner-id` всегда**, независимо от
`STRICT_OWNER_CHECK`. Удаление устроено как снятие привязки «media -> владелец»,
и без владельца снимать нечего. Остальные RPC при отсутствии заголовка и
выключенном строгом режиме работают в анонимном режиме.

## Основной сценарий

```
Upload ──> media_id, status=PROCESSING
   │
   ├─ (если просили обработку) GetMedia в цикле, пока status != READY
   │
   ├─ GetDownloadURL ──> presigned URL, скачивание мимо сервиса
   └─ DownloadStream ──> байты через gRPC
```

## Upload

Client-streaming. Первое сообщение - строго `init`, дальше только `chunk`.

```bash
FILE=photo.jpg
SIZE=$(stat -c%s "$FILE")
KEY=$(uuidgen)

{
  jq -nc --arg o "$OWNER" --arg f "$FILE" --argjson s "$SIZE" --arg k "$KEY" \
    '{init: {owner_id: $o, filename: $f, mime: "image/jpeg",
             expected_size: $s, idempotency_key: $k,
             processing: {make_thumbnail: true}}}'
  jq -nc --arg c "$(base64 -w0 "$FILE")" '{chunk: $c}'
} | $GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
    -d @ localhost:9090 media.v1.MediaService/Upload
```

```json
{ "mediaId": "6a2b...", "status": "PROCESSING" }
```

В примере файл уходит одним чанком - так проще читать. Настоящий клиент режет
поток сам, потому что действует потолок размера **одного** protobuf-сообщения
в 16 МиБ (`MaxRecvMsgSize` в `cmd/mediaservice/main.go`, значение захардкожено).
Разумный размер чанка - от 256 КиБ до 1 МиБ: мельче - накладные расходы на
кадр, крупнее - рост пиковой памяти без выигрыша.

### Поля `UploadInit`

| Поле | Обязательно | Кратко |
|---|---|---|
| `owner_id` | да | UUID, проверяется `buf.validate` |
| `filename` | нет | Исходное имя файла |
| `mime` | да | Заявленный тип |
| `expected_size` | нет | Заявленный размер, `0` - «не знаю» |
| `idempotency_key` | да | Ключ защиты от дублей |
| `processing` | нет | `make_thumbnail`, `transcode` |
| `ttl` | нет | Срок жизни объекта |

**`filename`** сохраняется как есть в колонку `orig_filename` и возвращается в
`Media.filename`. В ключ хранилища не попадает: оттуда берётся только
расширение и только как запасной вариант, если MIME своего не дал.

**`mime`** проверяется по `MIME_ALLOWLIST`, затем подтверждается magic bytes и
`ffprobe`.

**`expected_size`**, если задан, обязан совпасть с фактическим размером до
байта.

**`ttl`** приходит как `Duration` и в момент приёма превращается в абсолютный
`expires_at`. По его истечении reaper удаляет объект.

Обработка запрашивается для конкретных видов: `make_thumbnail` для audio и
`transcode` для image отвергаются с `INVALID_ARGUMENT` - но уже после приёма
байтов: вид определяет `ffprobe`, а он работает по готовому файлу. Без запроса
обработки объект остаётся в статусе `STORED` и никогда не станет `READY` - это
не ошибка, а конечное состояние.

### Что происходит с байтами

1. Чанки пишутся во временный файл в `UPLOAD_TEMP_DIR`, попутно считается SHA-256.
2. Первые 512 байт сверяются с magic bytes заявленного MIME.
3. Пауза между сообщениями больше `UPLOAD_IDLE_TIMEOUT` - `DEADLINE_EXCEEDED`.
4. Больше трёх подряд пустых чанков - `INVALID_ARGUMENT`.
5. После конца потока: сверка размера, проверка квоты по факту, `ffprobe`.
6. `ffprobe` даёт вид (image/video/audio) и метаданные. Класс заявленного MIME
   обязан совпасть с определённым видом.
7. Оригинал уходит в MinIO по ключу `{owner_id}/{media_id}/original.{ext}`,
   запись - в Postgres. Если просили обработку, в той же транзакции создаются
   задачи и статус становится `PROCESSING`.

`ffprobe` обязателен: без него `Upload` не работает вообще, поэтому в образе
стоит `ffmpeg`.

### Идемпотентность

Ключ уникален в паре `(owner_id, idempotency_key)`. Повтор разбирается **до
приёма тела**:

- Ключ не встречался - обычная загрузка.
- Ключ есть, «значимые параметры» те же и `expected_size` совпадает - возвращается
  существующий `media_id` **без ошибки**. Байты не читаются вовсе.
- Ключ есть, что-то из значимых параметров разошлось - `ALREADY_EXISTS`.
- Ключ есть, объект в статусе `deleting` - `ALREADY_EXISTS`.

Значимые параметры - это `mime`, `make_thumbnail`, `transcode` и `expires_at`
(`ParamsFingerprint` в `internal/media/fingerprint.go`). **Содержимое файла в
сверку не входит.** Повтор с тем же ключом и теми же параметрами вернёт старый
объект, даже если байты другие. Если для вызывающего важна защита от подмены
содержимого, ключ надо делать производным от содержимого - например, брать хеш
файла.

> **Ловушка: `ttl` ломает идемпотентный повтор.** `ttl` задаётся как
> длительность, а в отпечаток входит уже абсолютное `expires_at`, вычисленное
> в момент приёма. У двух вызовов момент приёма разный, значит отпечатки
> разные, значит повтор загрузки с тем же ключом и тем же `ttl` всегда даёт
> `ALREADY_EXISTS`. Обход на стороне клиента: при повторе не задавать `ttl`
> - тогда отпечаток совпадёт с сохранённым только если и в первый раз его не
    > было, - либо не использовать `ttl` вместе с повторами. Это дефект сервиса,
    > а не контракта; можно завести отдельной задачей.

### Коды

| Код | Когда |
|---|---|
| `ALREADY_EXISTS` | Конфликт ключа идемпотентности, см. выше |
| `RESOURCE_EXHAUSTED` | Превышена квота владельца или кончилось место |
| `PERMISSION_DENIED` | `x-owner-id` не совпал с `init.owner_id` |
| `UNAUTHENTICATED` | Неверный токен, либо строгий режим без `x-owner-id` |
| `DEADLINE_EXCEEDED` | Простой дольше `UPLOAD_IDLE_TIMEOUT` или дедлайн вызова |
| `INTERNAL` | Сбой БД или хранилища |

`INVALID_ARGUMENT` выделен отдельно: условий много, и они срабатывают на
разных этапах.

Протокол стрима:

- первое сообщение не `init`;
- пустой поток;
- повторный `init` внутри потока;
- больше трёх пустых чанков подряд.

Поля `init`, до приёма байтов:

- `owner_id` не UUID;
- пустой `mime` или `idempotency_key`;
- MIME вне `MIME_ALLOWLIST`;
- `expected_size` больше `MAX_UPLOAD_BYTES`;
- `ttl <= 0`.

Содержимое, по ходу приёма и после него:

- пустое тело;
- фактический размер не совпал с `expected_size`;
- magic bytes не соответствуют заявленному MIME;
- `ffprobe` не разобрал файл;
- класс заявленного MIME не совпал с определённым видом;
- `make_thumbnail` для audio или `transcode` для image: вид известен только
  после `ffprobe`, поэтому отказ приходит по уже принятому файлу.

## GetMedia

```bash
$GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
  -d '{"media_id":"6a2b..."}' \
  localhost:9090 media.v1.MediaService/GetMedia
```

```json
{
  "id": "6a2b...", "ownerId": "...", "kind": "IMAGE", "mime": "image/jpeg",
  "sizeBytes": "20480", "status": "READY", "metadata": { "width": 800, "height": 600 },
  "derivatives": [ { "variant": "thumb", "mime": "image/jpeg", "sizeBytes": "3120" } ],
  "createdAt": "2026-09-13T10:00:00Z", "filename": "photo.jpg"
}
```

Единственный способ узнать, что обработка закончилась. `status` проходит путь
`STORED` -> `PROCESSING` -> `READY` либо `FAILED`; при отказе причина лежит в
поле `error`. `derivatives` наполняется по мере готовности.

`expires_at` в ответе нет: TTL принимается на загрузке, но наружу не отдаётся.
Расхождение известное, решение продуктовое.

| Код | Когда |
|---|---|
| `INVALID_ARGUMENT` | `media_id` пуст или не UUID. |
| `NOT_FOUND` | Записи нет. |
| `PERMISSION_DENIED` | `x-owner-id` задан и не совпадает с `media.owner_id`, и нет строки в `media_attachments` для вызывающего. |
| `INTERNAL` | Сбой БД; либо `metadata` не разбирается в `google.protobuf.Struct`. |

## ListMediaByOwner

Keyset-пагинация по `(created_at, id)`.

```bash
$GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
  -d "{\"owner_id\":\"$OWNER\",\"page_size\":50}" \
  localhost:9090 media.v1.MediaService/ListMediaByOwner
```

`page_size = 0` означает серверный дефолт (50). Потолок - 1000, он проверяется
дважды: правилом `buf.validate` и явной проверкой в handler. Запрос большего
значения возвращает ошибку, а не молча обрезается.

Объекты в статусе `deleting` в выдачу не попадают: удаление начато, и
показывать их вызывающему нечестно. Объекты в статусе `failed` остаются -
владелец должен видеть неудавшуюся загрузку.

`next_page_token` непустой - есть ещё страница; его надо передать в
`page_token` следующего запроса. Токен - base64 от JSON с версией, `owner_id`
и курсором, и он привязан к `owner_id`: подстановка чужого токена даёт
`INVALID_ARGUMENT`, а не чужие данные.

| Код | Когда |
|---|---|
| `INVALID_ARGUMENT` | `owner_id` не UUID, `page_size > 1000`, испорченный токен |
| `PERMISSION_DENIED` | `x-owner-id` задан и не равен `owner_id`. |
| `INTERNAL` | Сбой БД. |

Отдельная запись, у которой `metadata` не разбирается, из ответа выпадает с
предупреждением в логе, а не роняет весь запрос.

## GetDownloadURL

Отдаёт presigned-ссылку прямо в хранилище. Трафик идёт мимо сервиса.

```bash
$GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
  -d '{"media_id":"6a2b...","variant":"thumb"}' \
  localhost:9090 media.v1.MediaService/GetDownloadURL
```

```json
{ "url": "http://minio:9000/media/...", "expiresAt": "2026-09-13T10:15:00Z" }
```

Пустой `variant` означает `original`.

**Ссылка никак не аутентифицируется.** Кто угодно, получив URL, скачает файл
до истечения `PRESIGN_TTL`. Отдавать её конечному пользователю можно, только
если это приемлемо; иначе - `DownloadStream`.

### Варианты

| Вариант | Кто создаёт | Для чего |
|---|---|---|
| `original` | `Upload` | Исходный файл. |
| `thumb` | задача `thumbnail` | Превью 320 px по ширине. |
| `r_720` | задача `transcode`, только video | Рендиция 720p, H.264 + AAC. |
| `preview` | задача `transcode`, для audio и image | m4a для audio, jpg для image. |
| `r_360` | **никто** | Не производится, см. ниже. |

`r_360` объявлен в `storage.Variant`, но не создаётся ни одним обработчиком.
Запрос такого варианта отвергается с `INVALID_ARGUMENT` заранее, чтобы не
отдавать вечный `NOT_FOUND`. Неизвестная строка варианта тоже даёт
`INVALID_ARGUMENT` до обращения к БД.

| Код | Когда |
|---|---|
| `INVALID_ARGUMENT` | `media_id` не UUID; вариант неизвестен или `r_360`. |
| `NOT_FOUND` | Нет записи media либо нет запрошенной производной. |
| `FAILED_PRECONDITION` | `original` при `FAILED`/`DELETING`; производная при статусе не `READY` |
| `PERMISSION_DENIED` | `x-owner-id` задан и не совпадает с `media.owner_id`, и нет строки в `media_attachments` для вызывающего. |
| `INTERNAL` | Сбой presign или пустой ключ хранилища. |

## DownloadStream

Server-streaming. Байты идут через сервис, хранилище наружу не светится.

```bash
$GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
  -d '{"media_id":"6a2b...","variant":""}' \
  localhost:9090 media.v1.MediaService/DownloadStream \
  | jq -r '.data' | base64 -d > out.jpg
```

Каждое сообщение - `DownloadChunk` с полем `data`. Тело не поднимается в
память целиком ни на сервере, ни в библиотеке.

Коды те же, что у `GetDownloadURL`. Отличие одно: ошибка может прийти уже
после начала потока, если соединение с хранилищем оборвалось на середине.
Клиент обязан считать скачивание успешным только после чистого конца потока,
а не после первого полученного чанка.

Когда что выбирать: `GetDownloadURL` дешевле для сервиса и даёт клиенту
докачку средствами хранилища; `DownloadStream` не выпускает наружу адрес
хранилища и уважает проверку доступа (owner или attachment) на каждом байте.

## DeleteMedia

```bash
$GRPCURL -H "authorization: Bearer $TOKEN" -H "x-owner-id: $OWNER" \
  -d '{"media_id":"6a2b..."}' \
  localhost:9090 media.v1.MediaService/DeleteMedia
```

Метод снимает привязку «media -> вызывающий», а не удаляет файл безусловно.
Одно media может быть привязано к нескольким владельцам (`media_attachments`,
счётчик `usages_count`). Пока привязки остаются, объект живёт; на нуле - запись
переводится в `deleting`, объекты в хранилище удаляются по префиксу
`{owner_id}/{media_id}/`, затем удаляется строка.

Загрузивший объект владелец привязывается к нему сразу: `Upload` создаёт строку
в `media_attachments` в той же транзакции, что и саму запись. Поэтому
`Upload` -> `DeleteMedia` работает без дополнительных шагов.

**Операция идемпотентна.** Повторный вызов на уже удалённом объекте возвращает
`OK`, а не ошибку: записи нет, удалять нечего, цель вызова достигнута. Значит
`DeleteMedia` можно безопасно повторять после `DEADLINE_EXCEEDED` или
`UNAVAILABLE`, не выясняя предварительно, дошёл ли первый вызов.

`NOT_FOUND` после этого означает ровно одно: **запись существует, но
вызывающий к ней не привязан.** Чаще всего - попытка удалить чужое.

| Код | Когда |
|---|---|
| `OK` | Привязка снята, либо снимать было нечего - см. ниже |
| `INVALID_ARGUMENT` | `media_id` не UUID, либо нет `x-owner-id` |
| `NOT_FOUND` | Запись есть, привязки вызывающего к ней нет. |
| `FAILED_PRECONDITION` | Статус `processing`: удалять нельзя, воркер потеряет файл. |
| `INTERNAL` | Сбой хранилища или БД. |

`OK` приходит в трёх разных случаях: привязка снята и объект удалён; записи
уже не было (идемпотентный повтор); привязка снята, но объект остаётся жив,
потому что к нему привязаны другие владельцы. То есть `OK` не означает «файл
удалён» - он означает «вашей привязки больше нет». Пока `usages_count` больше
нуля, объект живёт для остальных.

`INVALID_ARGUMENT` на отсутствующий `x-owner-id` - не оплошность: этому методу
заголовок нужен всегда, независимо от `STRICT_OWNER_CHECK`.

## DeleteByOwner

**Всегда возвращает `UNIMPLEMENTED`.** Отключён намеренно.

`x-owner-id` никем не верифицируется, а этот метод стирает всю медиатеку
владельца. Для одиночного `DeleteMedia` риск принят - максимум один чужой
объект за вызов. Для массового необратимого удаления тот же риск неприемлем:
достаточно подставить чужой UUID в заголовок и в тело. Доменная логика и её
тесты на месте; RPC включится, когда появится настоящая проверка идентичности
вызывающего. Комментарий в `internal/api/media.go` ссылается на #5.

Интерсептор `x-caller-id` из
[#21](https://github.com/GO-Masterskaya/media-service/issues/21) в цепочку
подключён, но задачу он решает другую: определяет вызывающего для лимитов и
allowlist, а право на конкретный `x-owner-id` не подтверждает. См. таблицу
лимитов ниже.

Массовое удаление сейчас доступно только встраиванием библиотекой, где
идентичность вызывающего задаёт сам встраивающий код.

## Health и readiness

| Проба | Где | Для чего |
|---|---|---|
| `GET /livez` | HTTP, `HTTP_ADDR` | liveness-проба |
| `GET /readyz` | HTTP, `HTTP_ADDR` | readiness-проба и балансировщик |
| `grpc.health.v1.Health/Check` | gRPC, `GRPC_ADDR` | то же в терминах gRPC |
| `grpc.health.v1.Health/Watch` | gRPC, `GRPC_ADDR` | поток изменений статуса |

**`/livez`** отвечает `200` всегда и зависимости не проверяет: она о том, жив
ли процесс, а не о том, может ли он работать.

**`/readyz`** отвечает `200`, если процесс не в drain и БД отвечает на ping,
иначе `503`.

**`Health/Check`** аутентификации не требует. Принимает два имени сервиса:
пустую строку и `media.v1.MediaService`; на любое другое отвечает `NOT_FOUND`.

**`Health/Watch`** перепроверяет БД раз в пять секунд и дополнительно на
каждое переключение статуса.

На том же порту отдаются метрики Prometheus:

```bash
curl -fsS localhost:8080/readyz
curl -fsS localhost:8080/metrics
grpc_health_probe -addr=localhost:9090
```

Метрики уровня RPC: `grpc_requests_total{method,code}`,
`grpc_request_duration_seconds{method}`, `grpc_active_streams` без меток. Рядом
живут внутренние счётчики с префиксами `media_upload_*`, `media_processing_*`,
`media_reaper_*`, `media_retention_*` и `reconciler_*`.

Эндпоинт аутентификации не требует и раскрывает имена методов, коды ответов и
объёмы трафика - держать его в служебной сети.

`grpcurl` для health-пробы не годится по той же причине, что и везде: без
reflection ему неоткуда взять дескриптор `grpc.health.v1`.

При получении `SIGTERM` сервис сначала переводит обе пробы в
`NOT_SERVING`/`503`, выдерживает окно для балансировщика и только потом
начинает `GracefulStop`. Порядок именно такой, чтобы балансировщик успел
увести трафик до закрытия соединений. HTTP-сервер гасится последним, чтобы
`/readyz` оставался доступен всё это окно.

## Лимиты

| Лимит | Значение | Действует |
|---|---|---|
| Размер одного protobuf-сообщения | 16 МиБ | Да, захардкожено |
| Размер файла | `MAX_UPLOAD_BYTES`, 500 МиБ | Да |
| Простой в стриме загрузки | `UPLOAD_IDLE_TIMEOUT`, 30 с | Да |
| Размер страницы | 1000 | Да, проверяется дважды |
| Квота владельца | `STORAGE_QUOTA_BYTES` или `storage_quotas` | Да, дважды |
| Запросов в секунду | `RATE_LIMIT_RPS` / `RATE_LIMIT_BURST`, 50/50 | Да |
| Одновременных стримов | `MAX_CONCURRENT_STREAMS`, 8 | Да |

Квота проверяется дважды: по заявленному `expected_size` и по фактическому
размеру после приёма.

Про две последние есть важная тонкость, которая ломает интуицию.
**Лимиты «на вызывающего» по умолчанию общие для всех.** Считаются они по
заголовку `x-caller-id`, но всё, чего нет в `CALLER_ID_ALLOWLIST`, попадает в
одно общее ведро. Списка по умолчанию нет, поэтому без настройки 50 rps и 8
стримов делятся между всеми клиентами разом. Отдельное ведро получает только
явно перечисленный идентификатор.

Превышение любого из двух даёт `RESOURCE_EXHAUSTED`. Health-методы из-под rate
limit выведены: иначе kubelet под нагрузкой перестал бы получать ответ и убил
бы под.

Keepalive на стороне сервера: idle-соединение закрывается через 15 минут, ping
раз в 5 минут с таймаутом 20 секунд. Клиенту запрещено пинговать чаще, чем раз
в 30 секунд, - более частый ping сервер сочтёт злоупотреблением и оборвёт
соединение.

## Повторные попытки

| Код | Повторять? | Как |
|---|---|---|
| `INVALID_ARGUMENT` | Нет | Запрос неверен. Повтор даст то же самое. |
| `ALREADY_EXISTS` | Нет | Ключ переиспользован либо работа уже сделана |
| `NOT_FOUND` | Нет | Два исключения, см. ниже |
| `PERMISSION_DENIED` | Нет | Чинить идентичность вызывающего |
| `UNAUTHENTICATED` | Нет | То же |
| `FAILED_PRECONDITION` | Иногда | Зависит от статуса объекта, см. ниже |
| `RESOURCE_EXHAUSTED` | Иногда | Зависит от причины, см. ниже |
| `DEADLINE_EXCEEDED` | Да | С тем же `idempotency_key` |
| `UNAVAILABLE` | Да | Экспоненциальный backoff с jitter, тот же ключ |
| `INTERNAL` | Осторожно | Один-два повтора с backoff |
| `UNIMPLEMENTED` | Нет | `DeleteByOwner` отключён |

**`ALREADY_EXISTS`** означает одно из двух: ключ идемпотентности
переиспользован с другими параметрами - тогда чинить вызов - либо это честный
дубль и работа уже сделана.

**`NOT_FOUND`** повторять бессмысленно, кроме двух случаев. Сразу после
`Upload` производная ещё может не существовать, но это ожидание готовности, а
не повтор. У `DeleteMedia` этот код означает чужой объект.

**`FAILED_PRECONDITION`**: объект в `PROCESSING` - подождать и повторить;
`FAILED` или `DELETING` - состояние конечное.

**`RESOURCE_EXHAUSTED`** приходит по трём разным причинам, и повторять стоит
не во всех. Квота владельца - только после освобождения места. Нехватка места
на сервере - повтор с backoff имеет смысл. Rate limit или лимит стримов -
повтор обязателен, но с задержкой не меньше секунды, иначе вызывающий сам себя
и держит. Различать по тексту ошибки: `rate limit exceeded` - это лимит,
`storage quota exceeded` - квота.

**`DEADLINE_EXCEEDED`** и **`UNAVAILABLE`** повторять обязательно с тем же
`idempotency_key`, иначе повтор создаст второй объект.

**`INTERNAL`**, если повторяется, - не транзиентная ошибка. Идти в логи по
`x-correlation-id`.
| `CANCELED` | Нет | Отменил сам вызывающий. |

Ожидание готовности обработки: push-уведомлений нет, единственный способ -
опрашивать `GetMedia`, пока `status` не станет `READY` или `FAILED`. Разумный
интервал - начать с секунды и расти до десяти. Верхняя граница ожидания -
примерно `JOB_MAX_ATTEMPTS × (JOB_BACKOFF_MAX + JOB_TIMEOUT)`; при дефолтах это
около часа для худшего случая с полным набором повторов. Если ждать столько
нельзя, ставить `JOB_MAX_ATTEMPTS` ниже.

## Расхождения со SPEC

| Тема | Что в SPEC | Что в коде |
|---|---|---|
| Формат Kafka-события | Плоский `{"type":"detach", ...}` | Конверт, см. ниже |
| `GRPC_AUTH_TOKEN` | «v1 не валидирует, пробрасывается» | Валидируется |
| `DeleteByOwner` | Обычный RPC | `UNIMPLEMENTED` |
| `ListMediaByOwner` | Отдаёт все записи владельца | `deleting` исключены |
| `RATE_LIMIT_RPS`, `MAX_CONCURRENT_STREAMS` | Лимит на вызывающего | Лимит на ведро |

Формат события - конверт `{"event_id", "event_type", "timestamp", "payload"}`
с типами `media.attach` и `media.detach`, подробности в
[`INTEGRATION.md`](INTEGRATION.md).

`GRPC_AUTH_TOKEN` валидируется в `TokenInterceptor`: при
`GRPC_AUTH_ENABLED=true` неверный токен даёт `UNAUTHENTICATED`.

`RATE_LIMIT_RPS` и `MAX_CONCURRENT_STREAMS` после #95 применяются, но не так,
как читается в SPEC: по умолчанию это общий лимит на всех, а не на каждого
вызывающего.
