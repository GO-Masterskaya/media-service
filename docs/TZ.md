# ТЗ — Media Service (Go)

Коробочный медиа-сервис: приём картинок/фото/видео/аудио, хранение в MinIO,
обработка через ffmpeg, привязка объектов к внешнему UUID, CRUD, опциональный
слушатель Kafka. Транспорт наружу — **только gRPC**.

---

## 1. Цель и контекст

Нужен переиспользуемый сервис хранения медиа, который можно подключать в разные
проекты как чёрный ящик. Проект-владелец даёт на вход свой `owner_id` (UUID) —
сервис принимает файл, валидирует, обрабатывает (ffmpeg), кладёт бинарь в MinIO,
метаданные в Postgres, и умеет по этому `owner_id` вернуть/удалить медиа.

Ключевые свойства коробки:
- Единственный внешний контракт — **gRPC proto** (это и есть публичный API).
- Инфраструктура (MinIO, ffmpeg, Postgres) — внутри, поднимается через `docker compose`.
- Конфиг через env, безопасные дефолты.
- Kafka-слушатель включается тоглом; без него сервис полностью рабочий.

## 2. Область

### В области
- gRPC API: upload (client-streaming), get metadata, get download URL, **download stream (отдача файла)**, delete, list by owner.
- Хранение бинарей в MinIO, метаданных — в Postgres.
- Пайплайн ffmpeg/ffprobe: валидация типа, извлечение метаданных, генерация превью, транскодинг.
- Асинхронная обработка тяжёлых операций (транскод/превью) через **горутин-движок** (channel-based воркер-пул, см. §3.2).
- Привязка медиа к внешнему `owner_id` (UUID), один owner → много медиа.
- Опциональный **TTL медиа**: задан → авто-удаление по истечении; не задан → хранится вечно.
- Kafka consumer за тоглом: события `attach` / `detach` (JSON), удаление объекта по `detach`, ошибки в DLQ-топик.
- Идемпотентность загрузки (по client-side `idempotency_key`).
- Rate limit / max concurrent streams per caller.
- Метрики (Prometheus), health/readiness, структурные логи.

### Вне области
- REST/HTTP наружу (только gRPC; допускается grpc-gateway как отдельная задача, не сейчас).
- UI/фронт.
- Аутентификация конечных пользователей (сервис доверяет вызывающему; token обязателен в контракте, но v1 его **не валидирует** — см. §5).
- CDN, гео-репликация, **антивирус-скан** (вне области).
- Редактирование медиа (обрезка/склейка по запросу пользователя).

## 3. Функциональные требования

### 3.1 Загрузка (client-streaming)
- Клиент шлёт стрим: первый чанк — `UploadInit` (owner_id, filename, mime, ожидаемый размер, idempotency_key, флаги обработки), далее — чанки байтов.
- Сервер:
  1. Валидирует `owner_id` (валидный UUID), размер (лимит из конфига), заявленный mime.
  2. Пишет входящий поток во временное хранилище (stream-to-temp, не держим весь файл в памяти).
  3. `ffprobe` определяет **реальный** тип/кодек/длительность/разрешение/битрейт. Если реальный тип не совпадает с классом заявленного (image/video/audio) — reject.
  4. Кладёт оригинал в MinIO (см. §6 layout).
  5. Пишет метаданные в Postgres со статусом `stored`.
  6. Если запрошена обработка (превью/транскод) — ставит задачу в очередь, статус `processing`.
  7. Возвращает `UploadResponse{ media_id, status }`.
- Идемпотентность: повтор с тем же `idempotency_key` + `owner_id` не создаёт дубль, возвращает существующий `media_id`.

### 3.2 Обработка (ffmpeg pipeline, async)
- **Валидация + метадата** (синхронно на upload): ffprobe → duration, width/height, codec, bitrate, frames, audio channels. Пишем в `media.metadata` (jsonb).
- **Превью/thumbnail** (async):
  - video → кадр на N-й секунде (конфиг, дефолт 1s) в jpg + опц. анимированный webp/gif.
  - audio → waveform png.
  - image → уменьшенный thumbnail (по большей стороне, конфиг).
- **Транскодинг** (async, тяжёлый):
  - video → нормализованный mp4 (h264 + aac), рендиция **720p** (единственная в v1).
  - audio → mp3/aac нормализация.
  - image → resize к целевым размерам + опц. webp.
- Производные объекты — отдельные записи `media_derivative`, ссылаются на родителя.
- Статусы медиа: `stored → processing → ready | failed`. `failed` хранит причину.
- **Горутин-движок очереди** (§3.6): задача персистится в `processing_jobs` (для восстановления после рестарта), но диспетчеризуется in-memory через каналы + пул воркеров-горутин. Конкуррентность ограничена конфигом (ffmpeg жрёт CPU).
- Ретраи обработки с backoff, max attempts из конфига; после исчерпания → `failed`.

### 3.6 Горутин-движок обработки
Собственный движок вместо тупого polling'а БД:
- **Диспетчер**: буферизованный `chan Job`, пул из `WORKER_CONCURRENCY` воркеров-горутин читают канал.
- **Backpressure**: канал ограничен; при переполнении новые задачи не теряются — лежат в `processing_jobs (status=queued)`, подхватываются фидером.
- **Фидер**: горутина, которая при свободных слотах доливает задачи из БД в канал (батчами, `run_after<=now`, `ORDER BY`), помечает `running`.
- **Recovery на старте**: задачи, зависшие в `running` (сервис упал) → возвращаются в `queued`.
- **Отмена/дедлайн**: каждая задача под `context` с таймаутом ffmpeg; отмена по graceful shutdown.
- **Graceful drain**: на shutdown фидер стоп, воркеры доделывают текущее в пределах таймаута, недоделанное → `queued`.
- **Наблюдаемость**: метрики глубины канала/БД-очереди, in-flight воркеров, времени обработки, ретраев.
- Никаких утечек горутин: всё под `errgroup`/`WaitGroup` + `context`, чистое завершение.

### 3.3 Чтение и отдача
- `GetMedia(media_id)` → метаданные + список производных + статус.
- `ListMediaByOwner(owner_id, pagination)` → страница медиа владельца.
- `GetDownloadURL(media_id, variant)` → **presigned GET URL** из MinIO (TTL из конфига). Вариант: `original` | `thumbnail` | `r_720`.
- `DownloadStream(media_id, variant)` → **server-streaming**, сервис сам отдаёт байты чанками (для приватных потоков без прямого доступа клиента к MinIO). Оба способа доступны — вызывающий выбирает.

### 3.4 TTL / авто-удаление
- В `UploadInit` опциональный `ttl` (или `expires_at`). Задан → медиа авто-удаляется по истечении. Не задан → хранится вечно.
- Реализация: поле `expires_at` в БД; фоновый reaper (горутина) периодически удаляет истёкшие (та же логика `DeleteMedia`).
- TTL распространяется на оригинал + все производные.

### 3.5 Удаление (CRUD delete)
- `DeleteMedia(media_id)` → **жёсткое**: удаляет запись + оригинал + все производные из MinIO. Идемпотентно (повтор на удалённом = OK).
- `DeleteByOwner(owner_id)` → каскадно всё медиа владельца.
- Мягкого удаления нет (решение — только hard delete).
- Удаление MinIO-объекта и записи БД — согласованно: сначала помечаем `deleting`, чистим MinIO, потом удаляем запись; фоновая уборка «зависших» (объект в MinIO без записи / запись `deleting` старше N).

### 3.7 Kafka listener (за тоглом)
- `KAFKA_ENABLED=false` по умолчанию. При `true` поднимается consumer.
- Формат события — **JSON**. Событие несёт: `type` (`attach` | `detach`), `owner_id`, `media_id`, `event_id`.
- `detach` → удаляет объект (та же логика, что `DeleteMedia`).
- `attach` → привязка/подтверждение связи (проставляет/валидирует `owner_id`).
- Обработка идемпотентна по `event_id` (событие могло прийти дважды).
- Consumer group, offset commit только после успешной обработки.
- **DLQ**: необрабатываемое событие (после ретраев) → в отдельный DLQ-топик (`KAFKA_DLQ_TOPIC`), offset коммитится, основной поток не встаёт.
- Тогл выключен → ни коннекта к Kafka, ни требований к её наличию.

## 4. Нефункциональные требования
- **Стриминг, не буферизация**: файл любого разумного размера не должен грузиться целиком в RAM.
- **Конкуррентность обработки** ограничена и конфигурируема; сервис не должен ложиться от параллельных транскодов.
- **Наблюдаемость**: Prometheus-метрики (кол-во загрузок, размер, длительность обработки, ошибки, глубина очереди), health `/livez` `/readyz` (или gRPC health-check service), структурные логи (slog) с correlation-id.
- **Graceful shutdown**: дождаться текущих задач/стримов в пределах таймаута.
- **Конфиг через env**, `.env.example` в комплекте.
- **Идемпотентность** upload и delete и Kafka-обработки.
- **Тесты**: unit на бизнес-логику, интеграционные на MinIO+Postgres (testcontainers), контрактные на gRPC. ffmpeg-шаги — на маленьких фикстурах.

## 5. Безопасность
- Транспорт gRPC: статический API-token в metadata **обязателен в контракте**. Но v1 сервис его **не валидирует** — доверяет gateway/mesh (реальная проверка вне сервиса). Interceptor читает/прокидывает token, но не реджектит. TODO на будущее: включить валидацию флагом.
- Валидация всех входных: UUID-формат, mime-allowlist, лимит размера, sanit имени файла (не используем сырой filename как ключ MinIO — генерим свой).
- ffmpeg/ffprobe запускаются на **файлах**, аргументы не собираются из пользовательских строк (без shell-инъекций; exec с массивом аргументов, никакого `sh -c`).
- Presigned URL — короткий TTL, отдельный bucket-policy (private).
- Секреты (MinIO keys, Kafka creds) — только из env/secret-store, не в логи.
- **Rate limit / max concurrent streams per caller** — есть (лимиты из конфига), защита от заваливания upload/транскодами.

## 6. Хранение

### MinIO layout
```
bucket: media (private)
  {owner_id}/{media_id}/original.{ext}
  {owner_id}/{media_id}/thumb.jpg
  {owner_id}/{media_id}/preview.webp
  {owner_id}/{media_id}/r_720.mp4
  {owner_id}/{media_id}/r_360.mp4
```
Ключ = наш сгенерированный `media_id` (UUID), не пользовательский filename.

### Postgres (эскиз)
- `media`: `id uuid pk`, `owner_id uuid idx`, `kind` (`image|video|audio`), `orig_filename`, `mime`, `size_bytes`, `status` (`stored|processing|ready|failed|deleting`), `storage_key`, `metadata jsonb`, `idempotency_key`, `expires_at` (nullable — TTL), `error`, `created_at`, `updated_at`. Уникальный индекс `(owner_id, idempotency_key)`, индекс по `expires_at` (reaper).
- `media_derivative`: `id uuid pk`, `media_id uuid fk`, `variant` (`thumbnail|preview|r_360|...`), `mime`, `size_bytes`, `storage_key`, `metadata jsonb`, `created_at`.
- `processing_jobs`: `id`, `media_id fk`, `type`, `status` (`queued|running|done|failed`), `attempts`, `last_error`, `run_after`, `locked_at`, timestamps. Забор через `FOR UPDATE SKIP LOCKED`.

## 7. Критерии приёмки (Definition of Done)
- [ ] `docker compose up` поднимает сервис + MinIO + Postgres; `.env.example` работает как есть.
- [ ] gRPC: upload картинки/видео/аудио стримом → объект в MinIO, метадата в Postgres, ffprobe-мета заполнена.
- [ ] Заявленный mime подделан (png с телом exe) → upload reject.
- [ ] Video upload с флагом обработки → появляются thumbnail + нормализованный mp4, статус доходит до `ready`.
- [ ] `GetDownloadURL` отдаёт рабочий presigned URL с TTL; по нему качается корректный файл.
- [ ] `DownloadStream` отдаёт корректный файл чанками через сам сервис.
- [ ] Upload с `ttl` → медиа авто-удаляется reaper'ом по истечении (оригинал + производные).
- [ ] `DeleteMedia` (жёсткое) чистит и БД, и все объекты в MinIO; повтор — идемпотентен.
- [ ] `ListMediaByOwner` пагинирует.
- [ ] Повтор upload с тем же idempotency_key не создаёт дубль.
- [ ] Горутин-движок: N параллельных транскодов не превышают `WORKER_CONCURRENCY`; рестарт во время обработки → задача восстанавливается (`running`→`queued`), не теряется; graceful shutdown доделывает/возвращает в очередь.
- [ ] Rate limit срабатывает при превышении лимита стримов/запросов per caller.
- [ ] `KAFKA_ENABLED=false` — сервис полностью рабочий, к Kafka не коннектится.
- [ ] `KAFKA_ENABLED=true` — событие `detach` (JSON) удаляет объект; дубль по `event_id` не ломает; битое событие уходит в DLQ-топик, поток не встаёт.
- [ ] Падение ffmpeg на битом файле → статус `failed` с причиной, сервис жив.
- [ ] Метрики (включая глубину очереди/in-flight воркеров) и health-чек отвечают; graceful shutdown дожидается задач; горутины не текут.
- [ ] Тесты: unit + интеграционные (testcontainers) зелёные; `go vet`, `go build ./...` чисто.

## 8. Решения (закрытые вопросы)
1. **Kafka формат** — **JSON** (`type`, `owner_id`, `media_id`, `event_id`).
2. **TTL медиа** — опциональный `ttl`/`expires_at`; задан → авто-удаление reaper'ом; не задан → **вечно**.
3. **DLQ Kafka** — отдельный **DLQ-топик** (`KAFKA_DLQ_TOPIC`).
4. **Удаление** — только **жёсткое** (hard). Мягкого/корзины нет.
5. **Отдача файла** — presigned URL **и** `DownloadStream` (приватный поток через сервис). Оба.
6. **Рендиции транскода** — только **720p** в v1.
7. **Очередь** — **горутин-движок** (in-memory каналы + пул воркеров), персист задач в БД для recovery. Не тупой polling.
8. **Антивирус-скан** — **вне области**.
9. **Auth транспорта** — token **обязателен в контракте**, но v1 **не валидирует** (доверяем gateway; валидация — TODO за флагом).
10. **Rate limit** — **делаем** (per-caller, из конфига).

Остаточные уточнения по ходу реализации:
- Семантика `attach` кроме проставления owner_id (нужен ли side-effect на видимость/TTL).
- Точная политика ретраев перед уходом события в DLQ (кол-во, backoff).
